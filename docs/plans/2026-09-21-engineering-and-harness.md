# GitHub 工程化与下一轮 Harness 实验整合计划

## 1. 目标与阶段

本计划替代前两版。当前仍处于规划阶段，尚未 commit、push 或创建 GitHub 仓库。

按每周 **30–40 小时**投入，预计分 **1–2 周**完成：

1. 发布现有 baseline，建立可重建、可回归的 GitHub CI。
2. 实现诊断复核与工具恢复，接入手动评测工作流。
3. 完成 **24 次开发对照＋12 次冻结验证**，形成保留或回退改动的证据。

现有 baseline 保留为独立版本：Holmes 原生评测 2/2 通过，外部诊断 1/3 成功，三条轨迹验收通过。本轮不预设提分目标。

## 2. GitHub 提交与基础 CI

**仓库与工作方式**

- 实施的首个写入动作，是保存本计划到 `docs/plans/2026-09-21-engineering-and-harness.md`；阶段结果另存 `docs/reports/`。
- 新建私有仓库 `kevinhimself711/sre-agent-project`。提交代码、非敏感配置、补丁、计划与报告；私人调研、算力资料、凭据、上游 checkout 和原始运行产物保留本地。
- 保留“固定上游 commit＋补丁”结构。补丁禁止换行转换，Shell 脚本固定 LF；本地提交前检查补丁与实际工作区是否一致。
- 使用当前 GitHub 账号的 noreply 身份，仅配置本仓库。先提交 baseline，再提交工程化配置与整合计划；验证远端私有状态和提交 SHA。
- 后续采用 `main`＋`codex/*` 分支与 PR。PR 模板记录问题、实现、验证、实验结论及局限。账号支持时设置 CI 必须通过的分支规则；不支持则明确记录，不自动购买套餐。

**依赖与提交检查**

- 根目录增加 `pyproject.toml`、`uv.lock`，管理自己的脚本和开发工具依赖，移除对 `.research/python-deps` 的隐式依赖。
- Holmes、SREGym 保留各自锁文件、工具版本和独立环境。
- 引入 pre-commit：Ruff、ShellCheck、actionlint、配置及大文件检查；使用 Gitleaks CLI 扫描源码和补丁。格式化工具不直接改写补丁；测试假 key 使用精确例外规则。
- Dependabot 初期只维护 GitHub Actions 依赖，每周归并更新；上游源码版本升级单独评审与回归。

**GitHub Actions CI**

PR 和 `main` push 自动运行，采用 Linux、Python 3.12，不读取模型或节点凭据：

1. 检查根目录代码、配置、补丁哈希和工作流。
2. 在干净目录检出固定上游版本并应用补丁。
3. 按各自锁文件安装环境，执行 Holmes hook/MCP/loop 相关测试，以及 SREGym adapter、轨迹、索引、导出和配置隔离测试。
4. 上传 JUnit 和检查摘要，由统一 `ci-gate` 汇总结果；纯文档变更跳过重测试，仍产生明确检查结果。

缓存按系统、Python、上游版本和锁文件区分。Actions 固定版本，默认使用只读权限。

修正历史报告中的测试表述：5 个 hook 测试断言通过，但当次命令未达到全仓覆盖率门槛。针对性子集使用 `--no-cov -n 0` 重跑并记录退出码，不降低上游全仓覆盖率要求。

## 3. Harness 改动与数据接口

**A：结束前的一次诊断复核**

- 在原生 loop 首次准备正常返回最终答案时，保留草稿并触发一次复核：检查当前症状、证据时间范围，以及可能推翻当前结论的观测。
- 使用同一模型、上下文和工具；可以继续调查，每个 attempt 最多触发一次。
- 所有额外调用计入原有 30 步与超时预算。预算不足、截断或异常结束时不追加复核，记录跳过原因。
- 默认关闭；提示不包含故障 ID、已知根因、注入信息或评分结果。

**B：MCP 错误语义与恢复**

- 扩展现有 MCP 结果处理，增加默认空、按 toolset 配置的文本错误规则，仅为 SREGym kubectl 启用。
- 识别返回开头的 `Command Rejected`，区分管道限制、RBAC 拒绝和其他明确拒绝。
- 保留原始结果，将状态标为 ERROR，同时向模型提供原始错误与对应恢复提示。模型在原有预算内决定下一步，不自动执行命令改写或重试。
- 普通日志正文中的错误描述不判为工具调用失败；保持 benchmark 服务端及权限配置一致。

**配置与轨迹**

- 提供 `baseline / review / recovery / combined` 四种配置，对应两个独立开关，默认均关闭。
- 实验清单固定案例、故障族、split、重复次数、顺序、模型和预算；记录代码、补丁、prompt、配置与镜像标识。
- trace 增加复核状态、草稿关联和工具错误分类，继续保存每次真实模型输入。
- 复用 ATIF、SQLite 与导出机制。被复核撤销的草稿不作为正样本监督目标；冻结验证案例禁止进入 SFT 导出。评分始终保留在宿主侧。

## 4. 手动评测工作流与实验设计

**运行方式**

- 增加薄的 campaign CLI，接受实验清单、`dev/validation` 阶段和续跑选项，复用上游部署、调查、评分与清理流程。
- 按 campaign、配置、案例、重复序号关联 attempt 和产物。续跑跳过已确认完成项；状态不明的 attempt 先核实与清理，必要时创建新 attempt，不从任意工具步骤恢复。
- GitHub 使用 `workflow_dispatch`，仅从 `main` 手动触发，运行已通过 CI 的固定提交。
- pci-2 配置仓库专用 self-hosted runner 和独立工作目录。参数化现有运行、构建及采集脚本的项目路径，避免覆盖开发工作区。
- workflow concurrency 与节点文件锁共同保证 `sre-agent-dev` 独占；手动 CLI 也使用同一把锁。运行中的评测不因新任务自动取消。
- 每次运行显式使用专用 kubeconfig，清理后检查环境；复位失败停止后续案例。取消和进程中断不能视为已完成清理，下次启动必须重新核实。
- 原始轨迹保留在节点和本地；GitHub 上传脱敏后的指标、测试报告和产物哈希，分别显示执行、诊断、评分及数据状态。

**固定实验矩阵**

| 阶段 | 案例 | 配置与重复 |
|---|---|---|
| 开发对照 | `network_policy_block`、`wrong_service_selector_social_network` | 四种配置各 3 次，共 24 次 |
| 冻结验证 | `namespace_memory_limit`、`readiness_probe_misconfiguration_social_network` | baseline 与选定候选各 3 次，共 12 次 |

- 保持现有 Agent/judge 模型与非思考模式、full profile、diagnosis、工具权限、30 步、8192 输出上限和 1800 秒超时。
- 固定种子 `20260921` 生成交错顺序，同一集群串行执行；历史运行只作背景，本轮重新运行 baseline。
- 开发完成后，从三个改动方案中依次按官方成功数、平均 composite score、Agent token 开销选择验证候选；完全持平选择组件更少的方案。baseline 同时作为保留改动的比较标准。
- 若没有质量或成本收益，优先验证具有明确错误语义修正的 recovery；不因必须选择候选而宣称改进有效。
- 冻结后不根据验证结果继续调参。两个新案例称为“本轮冻结验证集”，不宣称构成充分的独立泛化评估。
- Agent 超时和错误诊断计入失败。环境、judge 与数据故障分别记录；全轮最多增加 4 次替代 attempt，仍缺测则报告缺测。

## 5. 验收与后续交付

**工程验收**

- GitHub 私有仓库可以从干净 checkout 重建两个上游实现，CI 实际运行通过。
- 离线测试覆盖：关闭开关保持行为、复核只触发一次且不超预算、取消和异常、错误识别及误判、实际上下文保存、工具配对、草稿和验证集导出隔离。
- campaign 测试覆盖重复启动互斥、中断后续跑、完成项不重复计数、复位失败阻止后续运行。恢复和故障分支优先通过模拟测试验证，避免额外扩大真实实验规模。
- 两个现有原生 smoke case 各运行一次，验证集成回归；真实评分不作为普通 PR 的强制合并门槛。

**实验交付**

- 报告逐案例成功数、composite、输入/输出/缓存 token、调查耗时、工具拒绝与重复调用次数。
- 人工核对恢复是否取得所需观测，以及最终结论是否仍依赖历史错误；所有失败与无收益结果保留。
- 未覆盖的用量与账单费用标为未知。小样本结果只报告观察到的差异，不包装成稳定提分。
- A 无收益则回退；B 可凭错误语义正确性保留，但诊断效果单独报告。最终提交更新后的补丁、实验清单、结果报告和贡献边界。
